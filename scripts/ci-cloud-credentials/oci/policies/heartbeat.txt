# Bundle: heartbeat (Requirement 4.4 — nodes write their own
# kythira-last-heartbeat tag via Instance Principal)
# Consumer: oci_heartbeat_writer (include/raft/oci_heartbeat_writer.hpp),
#           running ON a pool instance, not in CI
# Provisioned live: August 12, 2026 (policies kythira-ci-instance-hb and
#           kythira-ci-artifacts, dynamic group kythira-ci-instance-dg,
#           bucket kythira-ci-artifacts, service gateway kythira-ci-sgw +
#           route rule)
#
# Two principals are involved, and they are different kinds of thing:
#
#   1. The INSTANCE, as an Instance Principal, matched by the dynamic group
#      kythira-ci-instance-dg:
#        Any {instance.compartment.id = '<compartment OCID>'}
#      (Dynamic-group rule values are QUOTED. Do not carry over the WIF
#      trust rule's unquoted-value requirement — that quirk is specific to
#      identity-domain impersonation rules, and quoting is mandatory here.)
#
#   2. The CI GROUP (kythira-ci), which delivers the writer binary: upload
#      to the bucket, create a pre-authenticated request, hand the PAR URL
#      to the instance through a freeform tag the static cloud-init script
#      polls the metadata service for.
#
# Policy kythira-ci-instance-hb (compartment):
Allow dynamic-group kythira-ci-instance-dg to read instances in compartment {COMPARTMENT}
Allow dynamic-group kythira-ci-instance-dg to use instances in compartment {COMPARTMENT}
# `use instances` is what covers UpdateInstance — the tag write. Same
# verb-family trap instance-pool.txt documents: reads pass without it and the
# failure is a 404 that looks like a wrong OCID.
#
# DELIBERATELY NOT narrowed to self-only. The obvious clause —
#   where request.principal.id = target.instance.id
# — was applied on August 12, 2026 and REVERTED the same hour, because it
# broke an unrelated principal in the same compartment: with the clause in
# place, the CI group's put_object to the kythira-ci-artifacts bucket failed
# with BucketNotFound/404 ("...or you are not authorized") on two consecutive
# dispatches (runs 31641076068 and 31641860637, 4 and 13 minutes after the
# policy write), while the same UPST's compute calls (ListInstances) kept
# succeeding — and the compartment audit log shows the policy update as the
# ONLY mutation between the last green run and the failures. The mechanism
# is a sharper version of the documented one (Policy Advanced Features,
# "Variables that Aren't Applicable to a Request Result in a Declined
# Request"): a condition variable that is inapplicable to a request declines
# the request rather than merely not matching the statement — and the
# services evaluate this inconsistently: Compute tolerated the clause for
# requests with no target.instance.id (ListInstances passed), Object Storage
# failed closed for a DIFFERENT principal covered by a DIFFERENT,
# unconditional policy. Variable-to-variable comparison is additionally
# undocumented (the syntax reference only shows variable-to-literal), so the
# write-time validator accepting it proves nothing.
# Consequence: any instance in the pool can read/tag-write ANY instance in
# this compartment. Accepted: the compartment holds nothing but CI
# resources, and the alternative demonstrably breaks the artifact-delivery
# path for everyone else in the compartment. Anyone re-attempting this must
# verify put_object BY THE CI GROUP still works afterwards, not just the
# heartbeat path — that is exactly the cross-principal breakage that made
# the first attempt look like a bucket outage.
#
# Policy kythira-ci-artifacts (compartment):
Allow group {GROUP} to manage object-family in compartment {COMPARTMENT}
# `manage` rather than `use`: creating a pre-authenticated request needs
# PAR_MANAGE, which only the manage verb carries. Scoped to the compartment,
# which holds nothing but CI resources.
#
# Exercised by a least-privilege principal: YES for both, August 12, 2026,
# at the granted (broad) scope — see above for why the self-only narrowing
# was attempted, measured, and backed out the same day.
# Instance side: a pool instance running oci_heartbeat_writer_node under
# Instance Principal performed GetInstance + UpdateInstance (the heartbeat
# tag write) against itself — the first code from this tree ever to run on
# an OCI instance. Group side: the kythira-ci-wif service user (via the CI
# job's UPST) uploaded the writer binary and minted the PAR on the same
# day's real-cloud dispatch. The bring-up chain that got there — a
# dynamically-linked libatomic absent from the cloud image, and cloud-init
# silently dropping non-ASCII bare user_data — is recorded in
# heartbeat-cloud-init.sh's header and cmd/oci_heartbeat_writer/'s
# CMakeLists; neither was a policy problem, and no policy statement here
# needed to change from its first draft.
