# Requirements Document

## Introduction

This document specifies the requirements for Google Cloud Platform (GCP)
support in Kythira: two `quorum_manager` implementations and one
`certificate_provider` implementation, closing the "Additional cloud
providers" item in `README.md`'s Production Readiness / Contributing
sections for GCP specifically (Azure, OCI, and Alibaba Cloud remain out of
scope for this spec).

- **`gcp_compute_quorum_manager`** directly manages Compute Engine (GCE) VM
  instances through the Compute Engine API — provisioning by calling
  `instances.insert`, assessing liveness by calling `instances.list`, and
  decommissioning by calling `instances.delete`. This is the GCP analogue of
  `aws_ec2_quorum_manager` and `docker_quorum_manager`, and is the primary
  implementation.
- **`gcp_mig_quorum_manager`** manages one zonal Managed Instance Group (MIG)
  per placement group (zone). It drives cluster size by resizing the MIG
  rather than calling `instances.insert` directly, inheriting instance
  template versioning, Spot VM support, and regional distribution from the
  MIG, while the quorum manager retains control over *when* capacity changes
  occur and *which* instance is decommissioned. This is the GCP analogue of
  `aws_asg_quorum_manager`.
- **`gcp_privateca_certificate_provider`** is a `certificate_provider`
  (`include/raft/certificate_provider.hpp`) implementation backed by Google
  Cloud Certificate Authority Service (CAS), the GCP analogue of
  `aws_acm_pca_provider`.

Both quorum manager classes satisfy `quorum_manager<Q, NodeId, Address,
GroupId>` from `include/raft/quorum_management.hpp` with
`placement_group_id_type = std::string` (a GCP zone name, e.g.
`"us-central1-a"`). `gcp_privateca_certificate_provider` satisfies
`certificate_provider<P>` from `include/raft/certificate_provider.hpp`.

Unlike AWS, where the EC2 instance ID doubles as the kythira `NodeId`
(Requirement 5 below explains why that trick does not transfer to GCP), both
GCP quorum managers generate the `NodeId` themselves and record the mapping
to the underlying GCE resource name via a deterministic naming scheme
(`gcp_compute_quorum_manager`) or an instance label
(`gcp_mig_quorum_manager`).

The implementations live in:
- `include/raft/gcp_client_config.hpp`
- `include/raft/gcp_compute_quorum_manager.hpp`
- `include/raft/gcp_mig_quorum_manager.hpp`
- `include/raft/gcp_privateca_certificate_provider.hpp` /
  `gcp_privateca_certificate_provider_impl.hpp`

The quorum managers are compiled behind `#ifdef KYTHIRA_HAS_GCP_SDK`, set by
the build system when `google-cloud-cpp`'s `compute_instances`,
`compute_instance_group_managers`, and `compute_zone_operations` components
are detected. The certificate provider is compiled behind a separate
`#ifdef KYTHIRA_HAS_GCP_PRIVATECA`, mirroring how `aws_acm_pca_provider` is
gated independently of `aws_ec2_quorum_manager`/`aws_asg_quorum_manager`
(Requirement 1).

## Glossary

- **`gcp_compute_quorum_manager`**: A `quorum_manager` implementation that
  manages GCE VM instances directly via the Compute Engine API.
- **`gcp_mig_quorum_manager`**: A `quorum_manager` implementation that drives
  one zonal Managed Instance Group per placement group.
- **`gcp_privateca_certificate_provider`**: A `certificate_provider`
  implementation backed by Google Cloud Certificate Authority Service.
- **placement group**: In this spec, a logical failure domain — a GCP zone
  (`"us-central1-a"`). Not to be confused with a GCP *placement policy*
  resource (below).
- **GCP zone / region**: A zone (`us-central1-a`) is the atomic location unit
  GCE instances are created in; a region (`us-central1`) groups zones. Kythira
  placement groups map one-to-one to zones, matching the AWS spec's AZ
  mapping.
- **GCE instance name**: The DNS-1035-label string (`^[a-z]([-a-z0-9]{0,61}[a-z0-9])?$`,
  max 63 chars) that is a GCE instance's primary identifier and the argument
  every Compute Engine API call addresses it by (`instances.get`,
  `.delete`, `.setLabels`, ...). Chosen by the caller for
  `gcp_compute_quorum_manager`; assigned by the MIG for
  `gcp_mig_quorum_manager` (Requirement 5).
- **GCE numeric instance ID**: A `uint64` assigned by GCP at creation time
  (the `id` field of the `Instance` resource), distinct from the name. Not
  used for addressing by any Compute Engine API call, unlike AWS's
  `i-XXXXXXXXXXXXXXXXX`, which is simultaneously the addressing key and a
  ready-made numeric value. This spec does **not** use the GCE numeric
  instance ID as the kythira `NodeId` — see Requirement 5.
- **kythira node ID**: The `NodeId` used at the Raft layer. Generated by the
  quorum manager itself (a random 63-bit value; see Requirement 5), not
  derived from any GCP-assigned identifier.
- **label**: A GCP resource metadata key/value pair, restricted to
  `^[a-z][-a-z0-9_]{0,62}$` for both key and value (lowercase, no colons,
  63-char limit) — unlike AWS's freeform (`Key`, `Value`) tag pairs, which
  permit colons and mixed case. This forces `kythira:cluster`-style AWS tag
  keys to become `kythira-cluster` on GCP (Requirement 6).
- **instance metadata**: A separate GCE per-instance key/value store (distinct
  from labels), readable from inside the guest via the metadata server
  (`http://metadata.google.internal/computeMetadata/v1/instance/...`) without
  additional credentials. Used for the operator-supplied startup script
  (`startup-script` key) and the `enable-guest-attributes` flag (Requirement
  8 AC 6).
- **guest attribute**: A write-enabled subset of instance metadata
  (`instance/guest-attributes/{namespace}/{key}`), gated per-instance by the
  `enable-guest-attributes = TRUE` metadata key. The guest writes a value via
  a local `PUT` to its own metadata server — no OAuth token or IAM permission
  needed on the guest's attached service account, unlike a normal
  `instances.setMetadata` call. An external caller reads a guest attribute
  back via `instances.getGuestAttributes`, which does require
  `compute.instances.getGuestAttributes` on the *caller's* credentials. Used
  for the heartbeat value written by the running kythira process (Requirement
  8 AC 5).
- **Managed Instance Group (MIG)**: The GCP analogue of an AWS Auto Scaling
  Group. This spec uses **zonal** MIGs only (one per placement group/zone),
  not regional MIGs — regional MIGs spread instances across zones
  automatically, which would fight kythira's own per-group topology control.
- **instance template**: An immutable GCE resource describing the
  machine type, boot disk, network, and metadata for instances a MIG creates.
  Analogous to an AWS ASG launch template. Created and versioned by the
  operator, outside this spec's scope — `gcp_mig_quorum_manager` only resizes
  an existing MIG, mirroring `aws_asg_quorum_manager`'s scope.
- **autohealing policy**: A MIG feature that automatically recreates
  instances failing a configured health check — the GCP analogue of an ASG's
  ELB health check type. Left configured, it would let GCP replace an
  instance kythira still considers live, causing a split-brain (Requirement
  16, mirroring AWS Requirement 10.3's `HealthCheckType == "EC2"` rule).
- **placement policy**: A GCP `resourcePolicies` resource of type
  `COLLOCATED` that packs instances onto low-latency, closely located
  hardware within one zone — the GCP analogue of an AWS `cluster`-strategy
  Placement Group. GCP has no direct analogue of AWS's `spread` or
  `partition` Placement Group strategies; per-zone kythira placement groups
  already provide zone-level spread (Requirement 10).
- **Spot VM**: GCP's preemptible-successor discounted, reclaimable instance
  type (`scheduling.provisioningModel = SPOT`), the analogue of an AWS Spot
  Instance.
- **Google Cloud Certificate Authority Service (CAS)**: GCP's managed private
  PKI service, accessed via
  `google::cloud::privateca_v1::CertificateAuthorityServiceClient`. The GCP
  analogue of AWS Certificate Manager Private CA.
- **CA pool**: A CAS resource grouping one or more Certificate Authorities
  under a shared IAM/issuance policy; certificates are requested against a
  pool (`projects/{project}/locations/{location}/caPools/{pool}`), not a
  single CA resource directly.
- **`google-cloud-cpp`**: Google's C++ SDK; provides
  `google::cloud::compute_instances_v1::InstancesClient`,
  `compute_instance_group_managers_v1::InstanceGroupManagersClient`,
  `compute_zone_operations_v1::ZoneOperationsClient`, and
  `privateca_v1::CertificateAuthorityServiceClient`.
- **Application Default Credentials (ADC)**: GCP's default credential
  resolution chain (`GOOGLE_APPLICATION_CREDENTIALS` env var, `gcloud auth
  application-default login` cache, GCE/GKE metadata-server-attached service
  account) — the GCP analogue of AWS's `DefaultAWSCredentialsProviderChain`.
- **`desired_topology`**: The `desired_topology<GroupId>` struct from
  `quorum_management.hpp`, expressing the target node count per zone.
- **zone operation**: GCP's async long-running-operation object returned by
  `instances.insert`/`.delete` and `instanceGroupManagers.resize`. Unlike
  AWS's `RunInstances`/`TerminateInstances`, which take effect essentially
  synchronously from the caller's perspective (subsequent `DescribeInstances`
  calls reflect state; no separate operation-completion step is required),
  every mutating Compute Engine call returns an `Operation` that must be
  polled to `status == DONE` via `zoneOperations.get` before the mutation is
  guaranteed visible (Requirement 4).

## Requirements

### Requirement 1: Build System Detection

**User Story:** As a developer building Kythira, I want the GCP
implementations to be compiled only when `google-cloud-cpp` is available so
that the project builds cleanly on machines without the SDK, following the
same optional-dependency pattern as `KYTHIRA_HAS_AWS_SDK`.

#### Acceptance Criteria

1. `CMakeLists.txt` SHALL call `find_package(google_cloud_cpp_compute
   QUIET COMPONENTS compute_instances compute_instance_group_managers
   compute_zone_operations)` and set `KYTHIRA_HAS_GCP_SDK` when all three
   components are found.
2. Both quorum manager headers SHALL be wrapped in
   `#ifdef KYTHIRA_HAS_GCP_SDK` / `#endif` so they compile to nothing when
   the SDK is absent.
3. A separate `find_package(google_cloud_cpp_privateca QUIET)` check SHALL
   define `KYTHIRA_HAS_GCP_PRIVATECA` independently of `KYTHIRA_HAS_GCP_SDK`,
   mirroring `KYTHIRA_HAS_AWS_ACM_PCA`'s independence from
   `KYTHIRA_HAS_AWS_SDK` (`.kiro/specs/certificate-authority/requirements.md`
   Requirement 8.4). An environment with the compute components but without
   `privateca` SHALL still build everything except
   `gcp_privateca_certificate_provider`, and vice versa.
4. Both `KYTHIRA_HAS_GCP_SDK` and `KYTHIRA_HAS_GCP_PRIVATECA` SHALL be
   propagated to consuming targets via `target_compile_definitions`.
5. `DEPENDENCIES.md` SHALL gain entries: `google-cloud-cpp ≥ 2.20 (compute
   component) — GCP Compute Engine and Managed Instance Group quorum
   managers` and `google-cloud-cpp (privateca component) — GCP Certificate
   Authority Service certificate provider`.
6. `vcpkg.json` SHALL gain a `google-cloud-cpp` port entry with features
   `["compute", "privateca"]`, mirroring the existing `aws-sdk-cpp` entry's
   `["ec2", "autoscaling", "acm-pca"]` feature list.
7. A new `Kconfig` menu `"GCP Integration"` SHALL be added alongside the
   existing `"AWS Integration"` menu, containing `config GCP_SDK` (default
   `y`, backs `KYTHIRA_HAS_GCP_SDK`) and `config GCP_PRIVATECA` (`depends on
   GCP_SDK`, default `y`, backs `KYTHIRA_HAS_GCP_PRIVATECA`) — mirroring the
   existing `AWS_SDK`/`AWS_ACM_PCA` symbol pair.

### Requirement 2: Shared GCP Client Configuration

**User Story:** As a library user, I want a single project/credentials/region
configuration struct I can fill once and pass to any GCP component, rather
than duplicating fields across three configuration structs.

#### Acceptance Criteria

1. A `gcp_client_config` struct SHALL be defined in
   `include/raft/gcp_client_config.hpp` (compiled unconditionally) with:

   | Field | Type | Default | Purpose |
   |---|---|---|---|
   | `project_id` | `std::string` | `""` *(required, non-empty)* | GCP project the resources live in |
   | `credentials_json` | `std::string` | `""` | Inline service-account JSON key; empty = use Application Default Credentials |
   | `endpoint_override` | `std::string` | `""` | Override REST endpoint (for a test double; see Requirement 22) |
   | `api_timeout` | `std::chrono::seconds` | `30s` | Per-call timeout |
   | `operation_poll_interval` | `std::chrono::milliseconds` | `2000ms` | Interval between `zoneOperations.get` polls |

2. When `credentials_json` is empty, the implementations SHALL construct
   clients using `google::cloud::MakeGoogleDefaultCredentials()` (ADC). When
   non-empty, `google::cloud::MakeServiceAccountCredentials(credentials_json)`
   SHALL be used instead. There is no `credentials_file_path` field — callers
   that have a key file read it into `credentials_json` themselves, keeping
   `gcp_client_config` free of filesystem I/O.
3. `gcp_client_config` SHALL be an aggregate (no user-declared constructors).
4. Every GCP component in this spec (`gcp_compute_quorum_manager`,
   `gcp_mig_quorum_manager`, `gcp_privateca_certificate_provider`) SHALL embed
   a `gcp_client_config gcp` field in its own configuration struct, mirroring
   how every AWS component embeds `aws_client_config aws`.

### Requirement 3: GCP Resource Naming and Label Validation

**User Story:** As a library user, I want configuration validation to catch
GCP naming-rule violations (label format, instance name length) at
construction time rather than surfacing them as a rejected Future from deep
inside a provisioning call.

#### Acceptance Criteria

1. A free function `is_valid_gcp_label(std::string_view)` SHALL be defined in
   `gcp_client_config.hpp`, returning `true` iff the value matches
   `^[a-z][-a-z0-9_]{0,62}$`.
2. A free function `is_valid_gcp_resource_name(std::string_view)` SHALL be
   defined, returning `true` iff the value matches
   `^[a-z]([-a-z0-9]{0,61}[a-z0-9])?$` (a GCE instance-name-shaped DNS-1035
   label).
3. Both `gcp_compute_quorum_manager` and `gcp_mig_quorum_manager` SHALL
   validate at construction that `cluster_name` satisfies
   `is_valid_gcp_label` (it is embedded in both a label value and, for
   `gcp_compute_quorum_manager`, an instance name — Requirement 5).
   Violations SHALL throw `std::invalid_argument`.

### Requirement 4: Zone-Operation Polling Helper

**User Story:** As a developer implementing either quorum manager, I want a
single shared helper for polling a Compute Engine zone operation to
completion so that the insert/delete/resize call sites don't each
reimplement polling and error-unwrapping.

#### Acceptance Criteria

1. A function template `wait_for_zone_operation(ZoneOperationsClient&,
   std::string project, std::string zone, std::string operation_name,
   std::chrono::seconds timeout, std::chrono::milliseconds poll_interval) ->
   kythira::future_default<void>` SHALL be defined in
   `include/raft/gcp_operation_wait.hpp`, shared by both quorum managers.
2. The helper SHALL poll `zoneOperations.get` at `poll_interval` until
   `status == DONE` or `timeout` elapses.
3. WHEN the operation completes with a non-empty `error` field THEN the
   returned Future SHALL be exceptional, with the exception message built
   from the operation's error code(s) and message(s).
4. WHEN `timeout` elapses before `status == DONE` THEN the returned Future
   SHALL be exceptional with a distinguishable timeout error (not conflated
   with an operation-reported error).
5. The helper SHALL check the fault injection point
   `"raft/gcp/zone_operation/poll"` on every poll iteration.

### Requirement 5: Node Identity Scheme — Why GCP Cannot Reuse AWS's Approach

**User Story:** As a maintainer, I want the node-identity design decision
recorded as a requirement (not just a design-doc aside) because it is the
single biggest structural difference from the AWS spec and shapes every
other requirement below.

#### Acceptance Criteria

1. Neither GCP quorum manager SHALL derive `NodeId` from the GCE numeric
   instance `id` field. Rationale: every Compute Engine API that addresses an
   instance (`instances.get`, `.delete`, `.setLabels`, `.setMetadata`) takes
   the instance **name**, not the numeric `id`; there is no
   name-from-numeric-id lookup call, so a `NodeId` built from the numeric ID
   would still require an `instances.list` scan to resolve to a name before
   any subsequent call could be made, defeating the purpose of a
   purely-computed reverse mapping (contrast AWS's `node_id_to_ec2_id`, which
   *is* the addressing key).
2. `gcp_compute_quorum_manager::provision_node` SHALL generate `NodeId` itself
   — a value drawn from a cryptographically-strong 63-bit random range (top
   bit clear, so the value is representable whether the instantiated
   `node_id_type` is signed or unsigned) — **before** calling
   `instances.insert`, and SHALL use it to construct the instance name
   deterministically (Requirement 6). This makes `node_id_to_instance_name`/
   `instance_name_to_node_id` pure string functions requiring no API call,
   preserving the AWS design's statelessness property even though the
   generation mechanism differs.
3. `gcp_mig_quorum_manager::provision_node` SHALL likewise generate `NodeId`
   via the same random-63-bit-value mechanism, but — because the MIG (not
   kythira) chooses the instance name — SHALL record the mapping via the
   `kythira-node-id` instance label (Requirement 13) rather than the name
   itself, and SHALL resolve `NodeId → name` via a labelled `instances.list`
   lookup in `assess_quorum`/`decommission_node` (Requirement 14 AC 5,
   Requirement 15 AC 1). This is the one respect in which
   `gcp_mig_quorum_manager` is *not* purely stateless, a direct consequence
   of MIGs owning instance naming; `aws_asg_quorum_manager` does not have
   this asymmetry because the EC2 instance ID is both the naming key and the
   `NodeId` source regardless of which AWS component created the instance.
4. On a name collision (`instances.insert` failing with `ALREADY_EXISTS` for
   `gcp_compute_quorum_manager`, or a `kythira-node-id` label collision
   detected before `setLabels` for `gcp_mig_quorum_manager`), `provision_node`
   SHALL regenerate a new candidate `NodeId` and retry, up to 5 attempts,
   before rejecting the Future. Given the 63-bit keyspace, a collision on the
   first attempt is expected to be effectively unobservable in practice; the
   retry exists for correctness, not because collisions are anticipated.

### Requirement 6: `gcp_compute_quorum_manager` Configuration

**User Story:** As a library user deploying a multi-zone Kythira cluster on
GCE, I want a configuration struct that captures all required instance
launch parameters so that I can construct the manager with a single
designated initializer and have the constructor validate the configuration.

#### Acceptance Criteria

1. A `gcp_compute_quorum_manager_config` struct SHALL be defined with:

   | Field | Type | Default | Purpose |
   |---|---|---|---|
   | `gcp` | `gcp_client_config` | `{}` | Project, credentials, endpoint |
   | `cluster_name` | `std::string` | *(required)* | Scope for labels and the instance-name prefix |
   | `machine_type` | `std::string` | `"e2-medium"` | GCE machine type (short form; zone-qualified internally) |
   | `boot_disk_image` | `std::string` | *(required)* | Image reference passed to `initializeParams.sourceImage` |
   | `boot_disk_size_gb` | `std::uint32_t` | `20` | Boot persistent disk size |
   | `network` | `std::string` | `"default"` | VPC network self-link or short name |
   | `subnetwork_by_group` | `std::map<std::string, std::string>` | `{}` | GroupId (zone) → subnetwork self-link or short name |
   | `service_account_email` | `std::string` | `""` | Attached service account; empty = no service account attached |
   | `service_account_scopes` | `std::vector<std::string>` | `{}` | OAuth scopes for the attached service account |
   | `node_port` | `std::uint16_t` | `7000` | Port the kythira process listens on |
   | `startup_script_template` | `std::string` | `""` | Shell script written to the `startup-script` metadata key; `{NODE_ID}`, `{NODE_PORT}`, `{CLUSTER}`, `{ZONE}` are substituted |
   | `topology` | `desired_topology<std::string>` | `{}` | Target counts per zone |
   | `provision_timeout` | `std::chrono::seconds` | `300s` | Max time to wait for instance `RUNNING` state (in addition to the insert-operation wait of Requirement 4) |
   | `poll_interval` | `std::chrono::milliseconds` | `5000ms` | Interval between `instances.get` polls during provision |
   | `placement_by_group` | `std::map<std::string, gcp_placement_policy_config>` | `{}` | GroupId (zone) → placement policy config; absent = no placement policy for that zone |
   | `spot` | `bool` | `false` | When `true`, instances are requested with `scheduling.provisioningModel = SPOT` |
   | `extra_labels` | `std::map<std::string, std::string>` | `{}` | Additional labels on every managed instance; each key/value SHALL satisfy `is_valid_gcp_label` |

2. `gcp_compute_quorum_manager` SHALL validate at construction time that
   `cluster_name` and `boot_disk_image` are non-empty, `node_port` is
   non-zero, `cluster_name` satisfies `is_valid_gcp_label` (Requirement 3),
   every group in `topology.groups` has a corresponding entry in
   `subnetwork_by_group`, and every key/value in `extra_labels` satisfies
   `is_valid_gcp_label`. Violations SHALL throw `std::invalid_argument`.
3. The instance name for a node SHALL be `kythira-{cluster_name}-{node_id}`
   truncated/validated to satisfy `is_valid_gcp_resource_name` at
   construction time against the worst-case (longest) `NodeId` decimal
   representation; a `cluster_name` long enough to make this name exceed 63
   characters for the max `uint64_t` value SHALL cause the constructor to
   throw `std::invalid_argument` rather than deferring the failure to a
   future `provision_node` call.

### Requirement 7: `gcp_compute_quorum_manager` Class Interface

**User Story:** As a library user, I want `gcp_compute_quorum_manager` to
satisfy `quorum_manager<gcp_compute_quorum_manager<NodeId, Address>, NodeId,
Address, std::string>` so that I can wire it into a Raft node without any
glue code.

#### Acceptance Criteria

1. `gcp_compute_quorum_manager<NodeId, Address>` SHALL satisfy
   `quorum_manager<gcp_compute_quorum_manager<NodeId, Address>, NodeId,
   Address, std::string>` with `placement_group_id_type = std::string`,
   verified by a `static_assert` in its header.
2. The class SHALL be defined in `include/raft/gcp_compute_quorum_manager.hpp`.
3. The class SHALL be move-constructible and move-assignable; copy is
   deleted (it holds an `InstancesClient` and a `ZoneOperationsClient`, both
   non-copyable in `google-cloud-cpp`'s connection-object model).
4. The class SHALL initialize its clients using the credentials and
   `endpoint_override` from `gcp_client_config` per Requirement 2 AC 2.
5. The class SHALL provide `maintain_quorum(cluster)` returning
   `kythira::Future<quorum_health<NodeId, std::string>>` per Requirement 17.

### Requirement 8: `gcp_compute_quorum_manager` Label, Metadata, and Guest Attribute Scheme

**User Story:** As an operator, I want every managed GCE instance to carry
well-known labels so that I can audit which instances belong to a cluster,
and so that the quorum manager can reconstruct state after a process restart
without keeping in-memory records.

#### Acceptance Criteria

1. Every instance created by `provision_node` SHALL carry these labels:

   | Label key | Value |
   |---|---|
   | `kythira-cluster` | `{cluster_name}` |
   | `kythira-node-id` | decimal string of the generated `NodeId` |
   | `kythira-group` | `{target_zone}` |
   | `kythira-managed-by` | `kythira-gce-quorum-manager` |
   | `kythira-market` | `"spot"` when `config.spot` is `true`; `"standard"` otherwise |
   | `kythira-placement` | `"none"` or `"compact"`, per Requirement 10 |

2. Any labels in `config.extra_labels` SHALL be merged in; they SHALL NOT
   override the six labels above.
3. Because the instance name is `node_id_to_instance_name(node_id)`
   (Requirement 6 AC 3) — a pure computation — the manager needs no
   `instances.list` call to look up the instance name from a node ID. The
   `kythira-node-id` label exists for operator visibility and filtering
   only, unlike `gcp_mig_quorum_manager`, where the equivalent label is load
   bearing (Requirement 5 AC 3).
4. The rendered `startup_script_template` (after `{NODE_ID}`/`{NODE_PORT}`/
   `{CLUSTER}`/`{ZONE}` substitution) SHALL be written to the instance's
   `startup-script` metadata key at creation time.
5. A `kythira/last-heartbeat` guest attribute (Unix timestamp, seconds, under
   namespace `kythira`, key `last-heartbeat`) SHALL be documented as written
   by the running kythira node process itself via a local, unauthenticated
   `PUT` to `instance/guest-attributes/kythira/last-heartbeat` on its own
   metadata server — requiring no IAM permission on the guest's attached
   service account, only that `provision_node` set
   `enable-guest-attributes = TRUE` at creation time (AC 6 below). It is read
   externally by `assess_quorum`/`maintain_quorum` via
   `instances.getGuestAttributes`, which requires
   `compute.instances.getGuestAttributes` on the *quorum manager's own*
   credentials — a permission the manager already needs alongside
   `compute.instances.get`/`.list`/`.insert`/`.delete`, not an additional
   operational burden placed on every fleet instance's service account the
   way a guest-side `instances.setMetadata` write would have been. Kythira
   does not write an initial value at provision time; its absence on a
   freshly created instance is expected and not treated as unreachable until
   `config.provision_timeout` has elapsed since creation.
6. `provision_node` SHALL include `enable-guest-attributes = TRUE` in the new
   instance's `metadata.items` at creation time (Requirement 10 AC 3), a
   prerequisite for AC 5's guest-attribute write to succeed. Omitting it
   causes the guest's local write to fail silently from kythira's
   perspective — the guest attribute simply never appears — so this key is a
   required, not optional, part of every `instances.insert` request this
   manager builds.

### Requirement 9: `gcp_compute_quorum_manager::assess_quorum`

**User Story:** As an orchestrator, I need `assess_quorum` to report which
nodes are live at the GCE infrastructure layer so that stopped or deleted
instances are detected without relying solely on an application-level
heartbeat.

#### Acceptance Criteria

1. `assess_quorum` SHALL accept the caller-supplied `cluster` vector (a list
   of `node_placement<NodeId, std::string>`). When the vector is empty, it
   SHALL return a healthy result immediately without making any GCP API call.
2. `assess_quorum` SHALL group the cluster vector by `group_id` (zone) and
   issue one `instances.list(project, zone, filter="labels.kythira-cluster =
   {cluster_name}")` call per distinct zone present — unlike AWS's single
   multi-AZ `DescribeInstanceStatus` call, because GCE's `instances.list` is
   zone-scoped.
3. `assess_quorum` SHALL derive the expected instance name for each cluster
   entry via `node_id_to_instance_name` (a pure computation, no lookup) and
   match it against the per-zone `instances.list` results.
4. A node is **live** when its expected instance name appears in the
   matching zone's list result with `status == RUNNING`.
5. A node is **unreachable** when its expected instance name is absent from
   the zone's list result, or present with any `status` other than
   `RUNNING` (`PROVISIONING`, `STAGING`, `STOPPING`, `STOPPED`,
   `SUSPENDING`, `SUSPENDED`, `TERMINATED`).
6. `quorum_status` SHALL be derived from the ratio of live to total nodes in
   the cluster vector, using the standard four-level mapping from
   `quorum_management.hpp`, applied globally.
7. Per-group health SHALL be computed from the `group_id` field of each
   `node_placement` in the cluster vector. The `target_count` for each group
   SHALL come from `config.topology`.
8. WHEN any per-zone `instances.list` call fails THEN `assess_quorum` SHALL
   return an exceptional Future; partial results from zones that succeeded
   before the failing call are discarded (no partial-health reporting).
9. `assess_quorum` SHALL NOT modify any GCP resources.
10. `assess_quorum` SHALL check the fault injection point
    `"raft/gcp/compute/list_instances"` before issuing each per-zone
    `instances.list` call.

### Requirement 10: `gcp_compute_quorum_manager::provision_node`

**User Story:** As an orchestrator that has detected a degraded placement
group, I need `provision_node` to launch a new GCE instance in the target
zone, wait for it to reach `RUNNING` state, and return its kythira node ID
and address so that the node can join the cluster via the normal
`ClusterJoin` flow.

#### Acceptance Criteria

1. `provision_node(target_group, replacing)` SHALL generate a new `NodeId`
   and derive the instance name per Requirement 5 AC 2 and Requirement 6 AC 3.
2. The new instance SHALL be launched in the subnetwork given by
   `config.subnetwork_by_group.at(target_group)`. When `target_group` is
   absent from `subnetwork_by_group` the Future SHALL be rejected with
   `std::invalid_argument`.
3. `provision_node` SHALL call `instances.insert` with:
   - `name`: the derived instance name
   - `machineType`: zone-qualified `config.machine_type`
   - `disks[0].initializeParams.sourceImage`: `config.boot_disk_image`
   - `disks[0].initializeParams.diskSizeGb`: `config.boot_disk_size_gb`
   - `disks[0].boot`: `true`, `disks[0].autoDelete`: `true`
   - `networkInterfaces[0].network`/`.subnetwork`: `config.network` and the
     resolved subnetwork
   - `serviceAccounts[0].email`/`.scopes`: `config.service_account_email`/
     `config.service_account_scopes` (the whole `serviceAccounts` entry
     omitted when `service_account_email` is empty)
   - `metadata.items`: the rendered `startup-script` (Requirement 8 AC 4) and
     `enable-guest-attributes = TRUE` (Requirement 8 AC 6)
   - `labels`: the label set from Requirement 8 AC 1–2
   - `scheduling.provisioningModel`: `"SPOT"` when `config.spot`; omitted
     (defaults to `"STANDARD"`) otherwise
   - `resourcePolicies`: the placement-policy self-link from
     `config.placement_by_group[target_group]` when present and
     non-`none` (Requirement 10 supersedes here — see cross-reference in
     Requirement 6's `placement_by_group` field; the placement-policy
     requirement itself is specified separately below as "Requirement 12")
4. `provision_node` SHALL await the returned zone operation via
   `wait_for_zone_operation` (Requirement 4). WHEN the operation reports an
   error (including `NAME_IN_USE` from a `NodeId` collision — Requirement 5
   AC 4) THEN `provision_node` SHALL retry with a freshly generated `NodeId`
   up to the attempt limit in Requirement 5 AC 4, or reject the Future with
   the underlying error once attempts are exhausted.
5. Once the insert operation completes, `provision_node` SHALL poll
   `instances.get` at `config.poll_interval` intervals until
   `status == RUNNING` or `config.provision_timeout` elapses.
6. Once the instance is `RUNNING`, `provision_node` SHALL read the primary
   internal IP from `networkInterfaces[0].networkIP` in the `instances.get`
   response and return `peer_info{new_node_id, "{internal_ip}:{node_port}"}`.
7. WHEN `instances.insert` (after exhausting retries) or the operation wait
   fails for a reason other than a name collision THEN the Future SHALL be
   rejected with the underlying GCP error; no cleanup is needed (no instance
   was created, or the failed operation left no running instance).
8. WHEN `provision_timeout` elapses before `RUNNING` state is reached THEN
   `provision_node` SHALL call `instances.delete` on the new instance
   (best-effort cleanup, itself awaited via `wait_for_zone_operation` with a
   short bounded timeout so cleanup cannot hang indefinitely) and return an
   exceptional Future.
9. The `replacing` hint, when non-null, SHALL be logged for diagnostic
   purposes. This implementation does not copy instance attributes from the
   replaced node.

### Requirement 11: `gcp_compute_quorum_manager::decommission_node`

**User Story:** As an orchestrator removing a broken node, I need
`decommission_node` to delete the GCE instance so that it cannot rejoin and
the project is not billed for a permanently broken node.

#### Acceptance Criteria

1. `decommission_node(node_id)` SHALL derive the instance name via
   `node_id_to_instance_name(node_id)` (a pure computation; no GCP API call
   needed) and call `instances.delete` with that name.
2. WHEN `instances.delete` returns a `NOT_FOUND` error (instance never
   existed or was already deleted) THEN `decommission_node` SHALL return a
   successfully-resolved Future (idempotent).
3. WHEN `instances.delete` fails for any other reason THEN
   `decommission_node` SHALL return an exceptional Future with the GCP error
   message.
4. After a successful `instances.delete` call, `decommission_node` SHALL
   await the returned zone operation via `wait_for_zone_operation`
   (Requirement 4) before resolving, ensuring a subsequent `assess_quorum`
   call reliably sees the instance as unreachable rather than observing a
   window where the delete has been accepted but not yet applied.
5. `decommission_node` SHALL NOT remove the node from the Raft cluster
   configuration — that is done by the `remove_server()` / `ClusterLeave`
   path.

### Requirement 12: Placement Policy Support

**User Story:** As a library user running a latency-sensitive Kythira
cluster on GCE, I want to specify a GCP placement policy per zone so that the
quorum manager places new nodes on low-latency, closely located hardware
when that matters for the workload.

#### Acceptance Criteria

1. A `gcp_placement_policy_config` struct SHALL be defined in
   `include/raft/gcp_compute_quorum_manager.hpp` (inside the
   `KYTHIRA_HAS_GCP_SDK` guard) with:

   | Field | Type | Default | Purpose |
   |---|---|---|---|
   | `self_link` | `std::string` | `""` | Resource policy self-link; empty means no placement policy |
   | `collocation` | `bool` | `false` | Informational; mirrors the policy's own `COLLOCATED` setting |

2. `gcp_compute_quorum_manager_config` SHALL contain
   `std::map<std::string, gcp_placement_policy_config> placement_by_group{}`
   mapping each kythira `GroupId` (zone) to its placement policy config.
   Absent entries mean no placement policy for that zone.
3. WHEN `placement_by_group[target_group].self_link` is non-empty THEN
   `provision_node` SHALL include it in the `resourcePolicies` array of the
   `instances.insert` request (Requirement 10 AC 3).
4. WHEN `placement_by_group` has no entry for `target_group`, OR the entry's
   `self_link` is empty, THEN `provision_node` SHALL omit `resourcePolicies`
   from the request entirely.
5. This spec provides no `spread`/`partition` equivalent: GCP has no
   placement-policy strategy analogous to AWS's `spread`/`partition`
   Placement Group strategies. Operators wanting zone-level spread already
   get it from kythira's own per-zone `topology` groups (Glossary,
   "placement policy").
6. The placement policy state SHALL be recorded in the instance label
   `kythira-placement` (value: `"none"` or `"compact"`, per Requirement 8 AC 1).

### Requirement 13: `gcp_mig_quorum_manager` Configuration

**User Story:** As a library user running a production cluster, I want a
MIG-backed quorum manager so that I can leverage instance templates, Spot VM
capacity, and MIG-managed instance replacement for transient VM failures,
while the quorum manager retains authority over *when* new nodes are added
or removed and *which* one is decommissioned.

#### Acceptance Criteria

1. A `gcp_mig_quorum_manager_config` struct SHALL be defined with:

   | Field | Type | Default | Purpose |
   |---|---|---|---|
   | `gcp` | `gcp_client_config` | `{}` | Project, credentials, endpoint |
   | `cluster_name` | `std::string` | *(required)* | Scope for label filters; identifies which instances belong to this cluster |
   | `mig_by_group` | `std::map<std::string, std::string>` | *(required, ≥1 entry)* | GroupId (zone) → zonal Managed Instance Group name |
   | `node_port` | `std::uint16_t` | `7000` | Port the kythira process listens on |
   | `provision_timeout` | `std::chrono::seconds` | `300s` | Max time to wait for a new instance to appear and reach `RUNNING` |
   | `poll_interval` | `std::chrono::milliseconds` | `5000ms` | Interval between `instanceGroupManagers.listManagedInstances` polls during provision |
   | `topology` | `desired_topology<std::string>` | `{}` | Desired counts per group (used by `topology()` and for validation only; not used to set MIG target size at construction) |

   There are no `heartbeat_timeout`/`heartbeat_grace_period` fields.
   Liveness is determined solely by GCE instance status via `instances.list`,
   mirroring `aws_asg_quorum_manager`'s equivalent decision.
2. `gcp_mig_quorum_manager` SHALL validate at construction that
   `cluster_name` is non-empty and satisfies `is_valid_gcp_label`
   (Requirement 3), `mig_by_group` is non-empty, `node_port` is non-zero, and
   every group in `topology.groups` has a corresponding entry in
   `mig_by_group`. Violations SHALL throw `std::invalid_argument`.
3. At construction, the manager SHALL call `instanceGroupManagers.get` for
   every MIG in `mig_by_group` and verify that `autoHealingPolicies` is empty
   (Requirement 16). If any MIG has a non-empty `autoHealingPolicies` the
   constructor SHALL throw `std::invalid_argument`.

### Requirement 15: `gcp_mig_quorum_manager::assess_quorum`

**User Story:** As an orchestrator, I need `assess_quorum` to determine which
kythira nodes are live at the GCE layer, reflecting actual instance status
rather than application-level heartbeats, in the presence of MIG-assigned
instance names that kythira does not control.

#### Acceptance Criteria

1. `assess_quorum` SHALL, for each distinct zone present in the cluster
   vector, call `instances.list(project, zone, filter="labels.kythira-cluster
   = {cluster_name}")` and build a `kythira-node-id` label → (name, status)
   map from the results.
2. A node is **live** when its `NodeId` appears as a `kythira-node-id` label
   value in the matching zone's results with `status == RUNNING`.
3. A node is **unreachable** when its `NodeId` does not appear in the zone's
   labelled results, or appears with any `status` other than `RUNNING`.
4. When the cluster vector is empty, `assess_quorum` SHALL return a healthy
   result immediately without making any GCP API call.
5. `quorum_status` and per-group health SHALL be computed using the same
   rules as `gcp_compute_quorum_manager::assess_quorum` (Requirement 9 ACs
   6–7).
6. WHEN any per-zone `instances.list` call fails THEN `assess_quorum` SHALL
   return an exceptional Future.
7. `assess_quorum` SHALL check the fault injection point
   `"raft/gcp/mig/list_instances"` before issuing each per-zone
   `instances.list` call.

### Requirement 16: `gcp_mig_quorum_manager::provision_node`

**User Story:** As an orchestrator, I need `provision_node` to increase the
target MIG's size by one, wait for the new instance to appear, and label it
with a fresh kythira node ID so that the resulting node can be identified by
`assess_quorum`/`decommission_node` afterward.

#### Acceptance Criteria

1. `provision_node(target_group, replacing)` SHALL identify the MIG name
   from `config.mig_by_group.at(target_group)`. When `target_group` is
   absent the Future SHALL be rejected with `std::invalid_argument`.
2. `provision_node` SHALL call `instanceGroupManagers.get` to read the
   current `targetSize`, then call `instanceGroupManagers.resize` with
   `size = current + 1`, awaited via `wait_for_zone_operation`.
3. After the resize operation completes, `provision_node` SHALL poll
   `instanceGroupManagers.listManagedInstances` at `config.poll_interval`
   intervals until an instance appears with `currentAction == NONE` (i.e.
   fully created, no pending MIG action) that does NOT yet carry a
   `kythira-node-id` label, or until `config.provision_timeout` elapses.
4. Once the new instance is found, `provision_node` SHALL generate a new
   `NodeId` per Requirement 5 AC 3, then call `instances.setLabels` with the
   label set from Requirement 8 AC 1 (using the MIG-assigned instance name,
   not a kythira-chosen one) and `kythira-managed-by =
   kythira-mig-quorum-manager`. `instances.setLabels` requires the current
   label fingerprint (read via a preceding `instances.get`); a
   `FAILED_PRECONDITION` fingerprint-mismatch response (another writer raced
   the labels) SHALL cause `provision_node` to re-read and retry the
   `setLabels` call up to 3 times before rejecting the Future.
5. WHEN the label set from step 4 collides with an already-used
   `kythira-node-id` (detectable because the pre-`setLabels` `instances.get`
   already shows a different instance with that label — practically
   unreachable given the 63-bit keyspace, but checked for correctness) THEN
   `provision_node` SHALL regenerate `NodeId` per Requirement 5 AC 4 and
   retry labelling.
6. `provision_node` SHALL then read the primary internal IP from
   `networkInterfaces[0].networkIP` (from the `instances.get` call in step 4
   or a fresh one) and return `peer_info{new_node_id,
   "{internal_ip}:{node_port}"}`.
7. WHEN `config.provision_timeout` elapses before step 3 finds a candidate
   instance THEN `provision_node` SHALL call `instanceGroupManagers.resize`
   to restore `targetSize` to its original value (best-effort rollback) and
   return an exceptional Future.

### Requirement 17: `gcp_mig_quorum_manager::decommission_node`

**User Story:** As an orchestrator, I need `decommission_node` to remove a
specific instance from its MIG and delete it, reducing the MIG's target size
so that the MIG does not immediately replace it.

#### Acceptance Criteria

1. `decommission_node(node_id)` SHALL resolve the instance name by calling
   `instances.list` filtered by `labels.kythira-node-id = {node_id}` across
   every zone in `mig_by_group` (there is no purely computed reverse mapping
   for MIG-managed instances — Requirement 5 AC 3). WHEN no matching instance
   is found in any zone THEN `decommission_node` SHALL return a
   successfully-resolved Future (idempotent — the node was already removed).
2. WHEN a matching instance is found, `decommission_node` SHALL call
   `instanceGroupManagers.deleteInstances` on its MIG with that instance's
   self-link, which both deletes the instance and decrements the MIG's
   target size atomically (the GCP analogue of AWS's
   `TerminateInstanceInAutoScalingGroup` with
   `ShouldDecrementDesiredCapacity = true`).
3. WHEN `deleteInstances` fails with `NOT_FOUND` THEN `decommission_node`
   SHALL return a successfully-resolved Future (idempotent).
4. WHEN the call fails for any other reason THEN `decommission_node` SHALL
   return an exceptional Future.
5. After a successful `deleteInstances` call, `decommission_node` SHALL
   await the returned zone operation via `wait_for_zone_operation`
   (Requirement 4) before resolving.

### Requirement 18: MIG Autohealing Conflict Guard

**User Story:** As an operator, I want the quorum manager to refuse to
operate against a MIG that has its own autohealing policy configured,
because two independent systems replacing instances based on different
liveness signals can each act on a node the other still considers healthy,
producing a split-brain — the same risk AWS's `HealthCheckType == "EC2"`
requirement (Requirement 10.3 of the AWS spec) guards against.

#### Acceptance Criteria

1. `gcp_mig_quorum_manager`'s constructor SHALL treat a non-empty
   `autoHealingPolicies` array on any MIG in `mig_by_group` as a
   configuration error (Requirement 13 AC 3).
2. This spec does not provide a mechanism to reconcile kythira's liveness
   view with a MIG autohealer's; operators wanting MIG-driven autohealing
   for transient VM failures MUST leave `autoHealingPolicies` unset and rely
   on kythira's own `maintain_quorum` remediation loop exclusively, matching
   the AWS spec's equivalent operational guidance.

### Requirement 21: `gcp_privateca_certificate_provider` Configuration and Interface

**User Story:** As a library user who wants `ca_service`/`ca_cluster_node` to
issue certificates from a managed CA instead of the in-process
`certificate_authority`, I want a `certificate_provider` implementation
backed by Google Cloud Certificate Authority Service, matching how
`aws_acm_pca_provider` backs the AWS case.

#### Acceptance Criteria

1. `gcp_privateca_certificate_provider` SHALL be provided in
   `include/raft/gcp_privateca_certificate_provider.hpp` /
   `_impl.hpp`, compiled only when `KYTHIRA_HAS_GCP_PRIVATECA` is defined
   (Requirement 1 AC 3), and SHALL satisfy
   `certificate_provider<gcp_privateca_certificate_provider>`, verified by a
   `static_assert`.
2. `gcp_privateca_certificate_provider_config` SHALL embed `gcp_client_config
   gcp` and additionally define:

   | Field | Type | Default | Purpose |
   |---|---|---|---|
   | `location` | `std::string` | *(required)* | CAS location (region), e.g. `"us-central1"` |
   | `ca_pool_id` | `std::string` | *(required)* | Pre-existing CA pool ID |
   | `certificate_authority_id` | `std::string` | `""` | Specific CA within the pool to pin issuance to; empty = let CAS choose within the pool per its own selection policy |
   | `certificate_template` | `std::string` | `""` | CAS certificate template resource name; empty = no template applied |
   | `validity` | `std::chrono::seconds` | `2592000s` *(30 days)* | Requested certificate lifetime |

   This component does NOT create or delete a CA pool or CA — provisioning
   one is an out-of-band operator action, mirroring
   `aws_acm_pca_provider_config`'s equivalent scope decision (its doc comment
   explicitly excludes CA lifecycle management).
3. `root_certificate_pem()` SHALL call
   `CertificateAuthorityServiceClient::GetCertificateAuthority` for
   `certificate_authority_id` (or, when empty, the pool's first `ENABLED` CA
   returned by `ListCertificateAuthorities`), caching the result after the
   first successful call, mirroring `aws_acm_pca_provider::root_certificate_pem()`'s
   caching behavior.
4. `sign_csr(csr_pem, options)` SHALL call
   `CertificateAuthorityServiceClient::CreateCertificate` with the CSR bytes
   set on `Certificate.pem_csr`, `config.certificate_template` applied when
   non-empty, and `lifetime` set from `config.validity`. Unlike
   `aws_acm_pca_provider::sign_csr` (which must poll `GetCertificate` after
   `IssueCertificate` because ACM Private CA issuance is asynchronous), CAS's
   `CreateCertificate` returns the issued certificate synchronously in its
   response — no poll loop is required.
5. `sign_csr` SHALL check the fault injection point
   `"raft/gcp/privateca/create_certificate"`, and `root_certificate_pem`
   SHALL check `"raft/gcp/privateca/get_certificate_authority"`, both before
   the corresponding API call, each compiling to a no-op when `FIU_ENABLE`
   is not defined.
6. `revoke(serial)` MAY be provided, calling
   `CertificateAuthorityServiceClient::RevokeCertificate`, mirroring
   `aws_acm_pca_provider`'s optional `revoke` (AWS spec Requirement 10 AC 7).

2. A unit test file `tests/gcp_quorum_manager_unit_test.cpp` SHALL be added

   labels `unit;gcp;quorum_manager`.
3. Unit tests SHALL use a fake `InstancesClient`/`InstanceGroupManagersClient`/
   `ZoneOperationsClient` connection layer (hand-written test doubles
   satisfying the same call interface `google-cloud-cpp`'s generated clients
   expose, injected via constructor overloads not present on the
   production-config constructor) rather than a network-level emulator.
   **Deviation from the AWS spec's three-tier model**: unlike AWS, GCP has no
   widely available, officially supported Compute Engine emulator equivalent
   to LocalStack, so this spec provides two test tiers (unit + real-GCP)
   rather than AWS's three (unit + LocalStack + real-AWS). This mirrors the
   test-double approach `tests/acme_test_server.hpp` already uses for
   `acme_certificate_provider` in this codebase, applied to a fake
   client layer instead of a fake HTTP server.
4. A unit test SHALL verify that constructing `gcp_compute_quorum_manager`
   with an empty `cluster_name` throws `std::invalid_argument`.
5. A unit test SHALL verify that constructing `gcp_compute_quorum_manager`
   with a `topology` group that has no corresponding entry in
   `subnetwork_by_group` throws `std::invalid_argument`.
6. A unit test SHALL verify that constructing `gcp_mig_quorum_manager` with
   an empty `mig_by_group` throws `std::invalid_argument`.
7. A unit test SHALL verify that constructing `gcp_mig_quorum_manager`
   against a fake MIG whose `autoHealingPolicies` is non-empty throws
   `std::invalid_argument` (Requirement 18 AC 1).
8. A unit test SHALL verify that `provision_node` with a `target_group` not
   present in `subnetwork_by_group` (`gcp_compute_quorum_manager`) or
   `mig_by_group` (`gcp_mig_quorum_manager`) returns an exceptional Future.
9. Chaos (fault injection) unit tests SHALL verify that enabling each fault
   point from Requirement 20 causes the corresponding call to return an
   exceptional Future.
10. A unit test SHALL verify the `node_id_to_instance_name`/
    `instance_name_to_node_id` round trip for `gcp_compute_quorum_manager`:
    `instance_name_to_node_id(node_id_to_instance_name(id)) == id` for a
    representative `NodeId`.
11. A unit test SHALL verify `is_valid_gcp_label` and
    `is_valid_gcp_resource_name` against both accepted and rejected example
    strings (uppercase, leading digit, colon, over-length).
12. A unit test file `tests/gcp_privateca_provider_unit_test.cpp` SHALL be
    added, registered as CTest target `gcp-privateca-provider-unit-tests`
    with labels `unit;gcp;certificate_authority`, exercising `sign_csr`/
    `root_certificate_pem` against a fake `CertificateAuthorityServiceClient`
    connection and the `"raft/gcp/privateca/*"` fault points.

##### Integration tests (real GCP)

13. Real-GCP integration tests SHALL be placed in
    `tests/gcp_quorum_manager_real_gce_test.cpp` and
    `tests/gcp_privateca_provider_real_test.cpp`, guarded by
    `KYTHIRA_GCP_REAL_TESTS=1`. They SHALL be excluded from the default
    CTest run and tagged `integration;gcp;real-gce` /
    `integration;gcp;real-privateca` respectively.
14. As the first action in setup, before any resource creation, the fixture
    SHALL call a lightweight read-only API (`projects.get` via the Cloud
    Resource Manager API, or equivalently the first `instances.list` call
    against the target project) using the configured credentials. If it
    fails for any reason (missing credentials, insufficient IAM roles,
    network error) the entire test suite SHALL be skipped (not failed),
    mirroring the AWS spec's `sts:GetCallerIdentity` pre-check (AWS spec
    Requirement 16 AC 9).
15. Real-GCP tests SHALL read the following env vars. Only `GCP_PROJECT_ID`
    and `GCP_REGION` are strictly required; the test SHALL skip (not fail)
    when either is absent. All other resources are created or auto-detected
    by the fixture when the corresponding env var is absent.

    | Variable | Required | Purpose |
    |---|---|---|
    | `GCP_PROJECT_ID` | Yes | GCP project for all created resources |
    | `GCP_REGION` | Yes | Region to derive test zones from (`{region}-a`, `{region}-b`, `{region}-c`) |
    | `GCP_TEST_IMAGE` | No | Boot disk image; when absent the fixture queries the latest `debian-cloud/debian-12` image |
    | `GCP_TEST_NETWORK` | No | Pre-existing VPC network; `"default"` used when absent |
    | `GCP_TEST_SUBNET_PREFIX` | No | Base name for auto-created per-zone subnetworks; `kythira-test` used when absent |
    | `GCP_TEST_SERVICE_ACCOUNT` | No | Pre-existing service account email for cluster instances; created if absent. No `compute.*` IAM role is required on it for kythira's own use — the heartbeat guest-attribute write (Requirement 8 AC 5) is a local, unauthenticated write from inside the guest — only, for the CAS test, a `privateca.certificateRequesters` role when this same service account is reused for the certificate-issuance test path |
    | `GCP_TEST_CA_POOL` | No | Pre-existing CA pool for the CAS integration test; created (with a self-signed root CA) if absent |
    | `KYTHIRA_NODE_BINARY` | Yes (quorum manager tests only) | Local path to the kythira-node binary, uploaded to a per-run Cloud Storage object for the startup script to fetch |

16. Each fixture SHALL generate a unique run ID and label every resource it
    creates with `kythira-test-run = {run_id}`, mirroring the AWS spec's
    `kythira:test-run` tag convention. Resources supplied via env vars are
    used as-is and are never deleted by the fixture.
17. Teardown SHALL destroy resources in reverse dependency order (cluster
    instances/MIGs first, then subnetworks, service accounts, CA pool/root
    CA last), executing every step unconditionally regardless of earlier
    step failures, collecting and printing all teardown errors to `std::cerr`
    without failing the test on cleanup errors — mirroring the AWS spec's
    teardown-ordering and error-collection rules (AWS spec Requirement 16 AC
    10).
18. Real-GCP `gcp_compute_quorum_manager` test cases SHALL cover, at minimum:
    `provision_and_assess_single_zone`, `provision_multi_zone_topology`,
    `stopped_instance_marked_unreachable`, `decommission_idempotent`,
    `spot_provision_and_decommission`, `provision_timeout_cleanup`
    (`provision_timeout = 1s`, verifying the exceptional Future and that the
    partially-created instance is deleted).
19. Real-GCP `gcp_mig_quorum_manager` test cases SHALL cover, at minimum:
    `mig_provision_increments_target_size`,
    `mig_assess_detects_non_running_instance`,
    `mig_decommission_decrements_target_size`,
    `mig_decommission_idempotent`,
    `mig_construction_rejects_autohealing_policy` (against a MIG the fixture
    deliberately configures with an autohealing policy).
20. A real-GCP `gcp_privateca_certificate_provider` test SHALL cover
    `sign_csr_returns_valid_certificate` (verify the returned certificate
    chains to the pool's root, matches the CSR's public key, and honors
    `certificate_template`/`validity`) and `root_certificate_pem_matches_pool_ca`.

### Requirement 24: CI Wiring — Replace the `gcp` Job Skeleton

**User Story:** As a maintainer, I want the existing no-op `gcp` job in
`.github/workflows/real-cloud-tests.yml` (scaffolded by
`.kiro/specs/ci-real-cloud-tests/`, whose own design.md names this exact
future spec as the place to fill it in) replaced with real steps, following
the same toggle and credential-federation pattern already established for
the `aws` job.

#### Acceptance Criteria

1. The `gcp` job SHALL gain the same resolution pattern as the `aws` job:
   `REAL_CLOUD_TESTS_GCP_ENABLED` (already scaffolded per
   `ci-real-cloud-tests/design.md`) gates the job; new
   `REAL_CLOUD_TESTS_GCP_QUORUM_MANAGER_ENABLED` and
   `REAL_CLOUD_TESTS_GCP_PRIVATECA_ENABLED` bundle-level variables gate the
   `gcp_quorum_manager_real_gce_test` (Compute Engine + MIG suites) and
   `gcp_privateca_provider_real_test` binaries independently, mirroring
   `REAL_CLOUD_TESTS_AWS_EC2_QUORUM_ENABLED`.
2. CI authentication SHALL use GCP Workload Identity Federation: a Workload
   Identity Pool and OIDC provider trusting `token.actions.githubusercontent.com`
   for a subject scoped to this repository (optionally narrowed to a ref or
   the `real-cloud-tests` GitHub Environment, mirroring Requirement 4.4 of
   `ci-real-cloud-tests`), impersonating a dedicated service account via
   `google-github-actions/auth@v2`'s `workload_identity_provider`/
   `service_account` inputs — no service-account JSON key is ever stored as
   a CI secret, matching the `aws` job's OIDC role-assumption posture with
   GCP's own native federation mechanism rather than a long-lived credential
   fallback.
3. A `scripts/ci-cloud-credentials/gcp/` directory SHALL be added, mirroring
   `scripts/ci-cloud-credentials/aws/`'s shape: a provisioning script
   creating the Workload Identity Pool/provider, the impersonated service
   account, and IAM role bindings scoped to exactly the enabled bundles; a
   `policies/` directory holding one IAM-binding fragment per bundle
   (`gcp-quorum-manager.json`, `gcp-privateca.json`); and a `README.md`
   walkthrough.
4. Test cost estimation and reporting (mirroring Requirement 20 of
   `aws-quorum-manager`) SHALL be added to
   `tests/gcp_quorum_manager_real_gce_test.cpp`, using published GCE
   on-demand machine-type pricing for the fixture's chosen instance shape,
   with an equivalent `TestCostReport`/`CostAccumulator`/
   `CostSummaryFixture` structure.
5. Signal-driven test cleanup (mirroring Requirement 21 of
   `aws-quorum-manager`) SHALL be added identically: SIGTERM/SIGINT/SIGHUP/
   SIGQUIT/SIGPIPE handlers invoke the active fixture's `teardown()` before
   re-raising, with the same async-signal-safety caveat documented at the
   handler definition.
